# Approved architecture 2.0.0 → implemented P0–P3

The approved plan/catalog is a roadmap; this branch implements its explicitly selected P0–P3 prefix plus the additive [unconfirmed editor persistence component](gateway.md), [connected vacancy/enhancement extension](../setup/connected-jobs-ai.md), [optional CV photo extension](../frontend/profile-photo.md) and bounded [import/enrichment extension](../setup/cv-import-enrichment.md). The latter uses a P4 migration prefix without implementing the roadmap's full P4–P7 scope. Counts below describe the resulting inventory, rather than a product requirement to reach a count. The frozen JSON catalog remains the detailed logical reference for the original model; it does not catalog these extensions. SQL is the exact physical implementation, including extra integrity/index columns below.

## Physical refinements within the approved model

Within the original P0–P3 model, concrete SQL adds precise reviewed-requirement controls (`scorable`, priority fraction, gate kind/equivalence permissions, atom ordinal), an application event ordering sequence, and explicit evidence-role/gate-state discriminators. These implement priority/eligibility/ordering already required by the plan. Eligibility assertions share the existing exact-lineage evidence graph; they are not new semantic score points. Their reviewed input is preserved in the pinned analysis bundle. Strict composite candidate keys/FKs include tenant plus appropriate stable profile/document/job and version IDs. Deferred triggers validate normalized revision/pin/projection consistency, not just UUID existence. The editor extension's separate immutable snapshot model is documented in the [gateway contract](gateway.md#unconfirmed-editor-state).

Entity kinds retain the canonical concepts: name, two positioning-title slots, contact, skill (professional/technical), employment, education, optional entry, enrichment. Claim and entity revision content is immutable; graph publication is atomic. Canonical facts projections, CV document layout/selection and job version inputs are distinct. Content changes allocate versions rather than rewriting the source Base CV while tailoring.

The SQL canonical validator embeds the [canonical schema](../../schemas/cv/v1/schema.json) without loosening its graph ID grammar. The [API contract](api.md#ids-at-the-canonical-boundary) owns ID allocation and decoding. Existing canonical fixtures and source ATS/duration calculators remain unchanged. Tests explicitly build separate relational evidence for the abstract ATS examples.

The template foundation changes only `validate_canonical`, with no new tables or policies. The [SQL API contract](api.md#template-publication) owns accepted references and publication limits; an inventory entry is not an executed SQL acceptance receipt.

## Executable evidence

`scripts/db/test.py` starts a private native PostgreSQL cluster and executes `supabase/tests/bootstrap.sql` plus all real migrations. Bootstrap Auth roles/subjects are local doubles. `supabase/tests/behavior.py`, `supabase/tests/editor_drafts.py`, `supabase/tests/connected.py`, `supabase/tests/photos.py` `supabase/tests/imports.py` and `supabase/tests/templates.py` supply executable behavioral methods; several include multiple races, source vectors or rejection cases. These are database behavior checks, not assertions that SQL source text happens to contain an expected string. The default `--suite all` includes all six suites and populated upgrades through P4. Both `--suite editor-drafts` and `--suite connected` run the editor and connected suites, skip the original behavior/import suites and populated upgrades, and still install all migrations and check normal reapply. `--suite photos` adds photo checks to the editor and connected suites. `--suite imports` runs only the import suite and the existing operation replay/worker-secret/unknown-attempt case; it also adds a permissive policy to the shared local Storage fixture to exercise the import isolation restrictions. This Storage policy coverage is specific to `--suite imports`; it does not establish hosted Storage API behavior. `--suite templates` runs only canonical template publication/restore and focused integrity/ownership checks after migration/reapply checks, without unrelated editor/connected/photo/import suites or populated upgrade.

## Explicit scope limits

P0–P3 is synchronous manual/reviewed evidence work. The connected extension adds synchronous operation/attempt accounting; its default-OFF generation boundary is owned by [connected setup](../setup/connected-jobs-ai.md). The bounded import extension's extraction and activation limits are owned by [import setup](../setup/cv-import-enrichment.md). No background worker, outbox/lease/fence job engine, webhook consumer, billing or rendering is activated. Those are later stages in the frozen plan, with their retry/unknown-effect requirements preserved there. This avoids adding a queue service before there is asynchronous work. Seven-day replay expiry is a technical guard, not an approved real-data retention policy. Deletion initiation/fencing exists; complete graph/object/Auth erasure and backup tombstone replay remain required before real personal data. Production data admission, automatic matching and the remaining P4–P7 roadmap are separate scopes. The [connected milestone's delivery ownership](gateway.md#pr-evidence-and-delivery-ownership) remains unchanged.

Photo migration/Storage helper prerequisites, physical cleanup limits, source resolution bounds and actual versus unverified cloud/export behavior are documented in [profile-photo.md](../frontend/profile-photo.md). Storage in native fixtures is an RLS/operation test double, not the HTTP object service.
