# Connected Job Workflow readiness

Implementation is local/tested with synthetic inputs. Inference remains **off** in the checked-in Worker configuration. No cloud migration, provider call, deployment or Store publication was performed. Stripe is deferred. Apply nothing to a hosted/owner database from this guide without the separate activation safeguards.

## Capture and processing

- Authenticated `POST /v1/jobs` saves the exact pasted source immediately, without Base. Request ID retries return the same durable draft; a new intentional capture gets its own draft.
- `POST /v1/jobs/url` saves a URL receipt before retrieval. Only exact vendor-owned public Greenhouse/Ashby/Lever/SmartRecruiters hosts are fetchable; redirects, auth pages, private/arbitrary destinations and oversized/unreliable content fail closed. A single structured posting is required. A saved URL is never presented as an extracted advert. Retry public retrieval, paste or extension fallback remains available.
- The MV3 extension uses its narrow existing account/device capture connection. Its collector prefers one bounded primary description or one unambiguous structured posting. Ambiguous/split pages require explicit selection/manual paste; no broad main/body scan, form/storage/account collection or automatic application. Installed Chrome/live ATS compatibility remains unverified.
- A durable worker operation is queued after capture. Request acknowledgement never waits for AI. The existing scheduled handler drains bounded work, and supported request execution contexts can wake one worker. Processing can continue after navigating away. Production/runtime scheduling is not established by a unit test.
- P05 extraction, reviewed manual corrections and original source remain separate. Source-span quotes, complete compound requirements, multiple categories, explicit priority, contextual emphasis, employment/geographic restrictions and uncertainty are validated. Manual corrections/reopening invoke no AI. Re-extraction cannot replace manual review.

`GET /v1/jobs/:job/workflow` is read-only. `.../review`, `/extract`, `/fetch`, `/match`, `/prepare`, `/tailor`, `/clarify`, `/action`, `/source`, `/cancel`, `/accept` use authenticated Origin/CSRF-checked POSTs. Account/job selectors are resolved by the existing user-scoped gateway; no page-supplied tenant authority. `/prepare` queues semantic matching, an independent semantic verification phase and persisted P07 suggestions, then a P08 proposal with claim verification. A saved vacancy review is required first; answering suggestions remains optional. These bounded phases share the operation ledger and source/target fences, with distinct attempt IDs and no inference on GET.

## Matching and tailoring

Runtime prompt/schema sources are `apps/api/src/jobs/operations.ts` (`jobPrompts`, `jobSchemas`), with executable synthetic examples in `apps/api/tests/job-workflow.test.mjs`. P05 is `vacancy-extraction/3`; semantic P06 is `job-evidence-match/1`; P08 is `job-tailor/1`. P03 remains career questions, not the full tailoring operation.

Matching compares eligible confirmed/authored Base facts and exact saved career answers against complete employer capabilities. Actual accepted CV text is a separate scope. Generated job wording never establishes new career facts. Deterministic `compatibility-1.2.0` aggregation retains the existing 30/25/15/10/10/5/5 category baseline, priority 3/2/1 and strengths 1/.75/.4/0; AND conserves importance and OR takes the maximum. Extra display categories map to the existing primary scoring groups. The indicators are **Profile Evidence Coverage** and **CV Evidence Coverage**, not employer ATS/hiring predictions. Eligibility conditions contribute to neither the ordinary numerator nor denominator; absent evidence does not prove lack of ability. Methodology is not empirically calibrated.

Persisted P07 recommendations group requirements supported by one experience, retain inclusion/dismissal state under semantic requirement/evidence identities, and offer skip-safe questions. Appearance-only saves do not change those identities. Exact answers go through the existing Base context/CAS API without changing CV prose or invoking AI. New evidence requires matching refresh.

P08 accounts for summary, positioning titles, both skill groups, every experience/project/custom entry, education, certifications and languages. Historical names, credentials and proficiency remain intact; education/certification/language descriptive details may be grounded rewrites or explicit retain decisions. Section regeneration is scoped; unchanged/rejected sections remain. Explicit acceptance patches only accepted targets in the current job CV, even after a Base change. Unsupported or uncertain semantic verification fails without replacing saved work. No live-model quality claim follows from injected verification fixtures. Source/job/Base/document pins, CAS and worker leases fence stale responses. Incomplete, invalid or interrupted results retain the saved source; interrupted paid work is not automatically redispatched.

The existing provider configuration/attempt ledger/fallback/cancellation interfaces are reused. Output stays within the existing 8,000-token cap; oversized inputs fail rather than silently truncate or increase budget. Fake transport tests establish contracts only, not real-model factual quality or latency. Paid/model-quality evaluation still needs separate authority.

Current content uses the existing editor/render envelope, stripped of Base import, raw Q&A and reference context while retaining document-owned hidden content. `fingerprint` hashes the current accepted content/presentation; `provenance.sourceFingerprint` is a different historical source hash.

There is exactly one current CV per owned job + `ro|en` locale. Saving overwrites that key. No tailored history, restore, old-content readback or visible revision labels remain. Internal CAS counters are not user history. `GET /v1/jobs/:job/cv` selects the primary current document; `?locale=ro|en` selects explicitly. `/cv/save` validates an accepted self-contained document. Historical selectors and history/restore paths are refused.

Internal `prepare_job_documents_for_base_removal(tenant)` is ungranted to PUBLIC/anon/authenticated and checks the owned caller. ### Legacy canonical current documents and Remove Base

Forward review artifact `20261030012000_p7_legacy_current_preservation.sql` preflights and converts supported current legacy job documents, attaches current edit links, and removes old canonical tailored content transactionally. An unsupported current document refuses the migration atomically. Its separate Base-removal transfer helper still requires import's later `require_base_cv_purge(tenant)` authority in the same transaction. No hosted/owner migration was applied during development.

The converter deliberately supports identity, selected plain-text contacts/skills, and one approved user-authored summary with supported fixed headings/default template. It preserves the resolved photo asset/crop/shape/visibility exactly. Other sections, structured claim values, AI prose, unsupported headings/templates, ambiguous references and differing current content at the same job+locale key refuse atomically. Two legacy locales without an existing primary current document also refuse rather than invent a primary language. This is a compatibility subset, not a general canonical renderer or universal conversion claim.

Identical accepted candidates deduplicate deterministically; different content never gets a timestamp winner. The helper writes only the existing `job_editor_*` current store and creates a missing target context from exact owned reviewed job text. It attaches `applications.current_job_document_id`; original chosen/sent canonical UUIDs remain opaque historical metadata. A current CV is never presented as the exact text sent previously. Search exposes current edit pointers separately from old sent metadata. Canonical job save/restore commands and old-content read fallbacks retire for every Base generation. Unsupported current legacy documents refuse the transaction before any content is removed; they do not leave an alternative history writer enabled. Base restore behavior remains separate.

Import owns deletion of the full old canonical/profile/analysis dependency closure after this helper succeeds, including old/current canonical job content and photo references. The helper itself does not duplicate that ordered purge. A refusal must surface as failed removal with all content retained, never a success message. Full Remove Base behavior requires the final import migration and integration checks; the native job suite uses a private synthetic fixture for its exact authority seam when that later migration is absent.

Hiding sections, contribution groups or individual fields is presentation only. Current saves and Base-removal preservation retain their document-owned content. CV evidence uses rendered order, visibility and valid wording, independently of eligible Profile evidence. Imported summaries share the core sourced Summary with editing and P08.

## Permanent job deletion

My Jobs cards and the opened job workspace offer **Delete job**, with a confirmation naming the posting and explaining that all its tailored CVs are permanently deleted. The authenticated, same-origin/CSRF-protected `POST /v1/jobs/:job/delete` accepts only `{requestId}` and calls the owned `delete_target_job` RPC. A successful receipt is `{jobId,deleted:true}`. The UI keeps a job visible after an unconfirmed result and reuses the request identity on retry; success retires that job's cached documents, answer commands and review drafts, including its open CV panes.

The forward migration `20261103153334_p8_permanent_job_deletion.sql` deletes the owned posting, its current CVs in all languages, linked source and analysis records, submitted intake and job-specific answers/reviews together. Profile snapshots, career facts, other jobs, shared photo assets and provider-attempt accounting are preserved. Exact-row transaction authority permits only the intended job closure through immutable-record guards. Tenant-first locking serializes deletion with processing and CV saves; failure rolls back the entire closure.

Content-free capture/intake/job fences reject replay of deleted resources. Existing paid work is fenced from publishing after removal; deleting a job does not reverse provider charges already incurred. A fresh intentional capture with a new request identity can create a new job. Historical workflow receipts without a recoverable job identity may be expired during deletion to prevent replay of removed content; this does not erase another job's saved state.

Focused native verification: `python3 scripts/db/test.py --suite job-deletion --pg-bin /path/to/postgresql/16/bin` (supply relocated share/library paths when needed). Browser fixtures exercise cancellation, acknowledged deletion, preserved other jobs and persistence after refresh without deleting customer data.
