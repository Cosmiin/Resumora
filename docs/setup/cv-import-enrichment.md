# CV import and career enrichment

This implementation connects authenticated document intake, unconfirmed review, exact saved Q&A and selected-role semantic wording proposals to the existing Worker/Supabase/editor persistence and AI attempt ledger. Paid execution remains OFF. No hosted migration, bucket, secret, provider request or real CV was used to validate it. The earlier quote-composition endpoint remains available; whole-role rewriting uses the separate structured operation below.

## Customer journey and saved truth

1. Choose PDF, DOCX or DOC, then explicitly upload/analyse. All source files are limited to **10,000,000 bytes**. PDF has an exact maximum of **10 pages** counted from its parsed page tree, including scanned/mixed documents. Word uses bounded text/container processing and native provider reading; original Word pagination is unknown, and a ten-page Word guarantee is intentionally absent.
2. The authenticated Worker verifies type/content and size, creates an owned private source/import record, and performs deterministic bounded preflight. It never executes document scripts, Office, local OCR or external document resources. A small configured AI model classifies CV / not-CV / uncertain. Only CV admission triggers the stronger extraction model. Both stages are metered separately. Non-CV/uncertain results stop; there is no automatic escalation or expensive rerun.
3. Extraction creates candidates with field path, source quotation, PDF page (Word `null`), confidence and warnings. These are **extracted_unconfirmed**, including high-confidence output. Provider-native transcription is not an independently verified quotation: the review warns about visual/Word evidence. Missing names, dates and figures stay missing; a full name is never automatically split into first/last name. Opening a recovered review starts a new draft rather than merging over newer edits.
4. The owner of the CV inspects/edits fields, selects confirmations and clicks **Confirm and save reviewed CV** once. Completion validation runs first. Selected matching imported facts become user-confirmed and a checkpoint plus immutable review-selection record is saved in one transaction, guarded by the current revision. Incomplete work autosaves separately; no checkpoint or canonical publication is fabricated. Unselected facts remain pending. Manual corrections remain independently authored facts.
5. In enrichment, select a role and explicitly request AI questions. The saved confirmed/authored role facts and relevant prior answers guide up to three questions with up to six neutral options each. No answer is preselected. Single/multiple/zero choices and optional text/text-only are supported. Save-and-next, skip and unknown are deterministic; no inference runs per keystroke. Exact question, options, selections, text and status persist in editor snapshots independently of CV contributions. **Add to CV** is optional and explicit; removing that copy retains Q&A.
6. **Propose experience rewrite** sends only the selected role's eligible context and saved confirmed Q&A. It returns a complete cited semantic rewrite, saved as a pending before/after review. Edit/Accept/Reject are explicit. Accept changes the selected presentation wording overlay; original facts and Q&A survive. Source changes invalidate accepted wording. Source IDs and numeric-token checks reject some unsupported output, but do not prove semantic entailment: inspect meaning before accepting. Prompt tone, quality and exact apply-back behavior remain subjects for the later owner workshop.

This is editor-draft persistence, not publication of confirmed canonical career claims or a canonical Base CV version. The source manifest reuses the existing unpublished personal-profile shell/source/span boundaries. No ATS semantic score, readability score, vacancy tailoring, photo processing or export is added by this feature.

## Runtime and input bounds

PDF preflight uses the pinned maintained `@cantoo/pdf-lib` fork inside the Worker. It traverses actual page-tree children rather than trusting `/Count`, rejects encrypted/malformed documents and bounded dangerous object structures, and uses depth/node/object limits. All accepted PDF pages are passed to the configured native vision/file route. There is no native OCR subprocess and no hosted Workers Free CPU/memory guarantee. Network-denied workerd tests cover mixed/scanned structure, forged counts, 11 pages, nested JavaScript, malformed input and near-10MB sources; pathological compressed structures and real document quality still need activation evaluation.

DOCX uses `fflate` with ZIP checks, bounded streamed expansion, no encrypted/macro/DTD input, 10MB total expanded bytes, 500KB individual relevant XML and 1MB aggregate relevant XML. Extracted relevant text is limited to 40,000 characters. Legacy DOC uses `cfb` to inspect OLE/WordDocument, reject encryption/macros/embedded objects and conservatively limit WordDocument bytes to 40,000 and metadata to 160,000. Formatting-heavy legacy files may be rejected even when visually short. `cfb` is a small older dependency (1.2.2); dependency maintenance remains an explicit operational risk. No Office converter/service is installed. Provider-native Word reading is text based; Word image OCR is not promised.

Structured extraction allows at most 250 candidates and 40,000 combined candidate-value/quote characters. Partial dates are year or month/year, with uncertain dates left pending. Career context is bounded to 24 facts, 2,000 characters per fact and 8,000 total; confirmed answers retain their own identities even when also copied into CV fields. Whole-experience wording stays active only while the complete accepted input matches, including uncited facts and confirmed answers. It omits identity/contact/employer/raw document fields, but role free text can still contain personal information; minimization is not anonymization.

## Provider seam and operation contracts

Reuse the existing session/CSRF and durable operation/attempt store. Raw binary is allowed only for the exact import POST; other write routes keep JSON protection. No client tenant/owner ID, arbitrary provider URL, model or schema is accepted.

| Explicit action | Provisional operation/version | Input/output contract | Route |
| --- | --- | --- | --- |
| Upload/analyse, stage 1 | `cv.admit.v1-provisional` | trusted file/page bounds → CV/not-CV/uncertain + reason/evidence pages | PDF: OpenRouter native-file primary, one direct OpenAI fallback; Word: direct OpenAI Responses |
| CV admitted, stage 2 | `cv.extract.v1-provisional` | same bounded source → unconfirmed candidates + evidence/warnings | Same format-specific route, stronger configured model |
| Prepare AI questions | `career.questions.v1-provisional` | owned saved snapshot/role/prior Q&A → bounded neutral questions/options | Existing OpenRouter primary/direct OpenAI fallback |
| Propose role rewrite | `career.role-rewrite.v1-provisional` | owned saved snapshot/role/evidence → cited pending full-role wording | Existing OpenRouter primary/direct OpenAI fallback |
| Save/skip/confirm/accept/reject | deterministic, no AI | validation, revision fence, persistence | Worker/Supabase/editor |

Strict structured schemas and domain validation treat document instructions as data; no tools or external URLs are enabled. Output token limits are admission 300, extraction 8,000, questions/rewrite 1,800. Attempts use 8 seconds for admission or 25 seconds otherwise, bounded by 30 seconds total per stage; the outer operation is 90 seconds and upload body reading 15 seconds. These are limits, not latency promises. One documented availability fallback is permitted for PDF/career; refusals, malformed output, invalid evidence, auth/policy errors and cancellation stop. Word uses documented direct `/v1/responses` input-file support for DOC/DOCX, with no assumed Chat Completions/Router Word support and no extra fallback.

No final prompts/models/prices are silently selected. Amounts are deferred; bounded tokens/time/attempts are not a monetary quota. Each attempt records usage and reported cost if available; missing prices, timeouts and abandoned requests retain unknown cost rather than zero. Both stages can incur charges; cancellation cannot undo them. Native PDF engines/provider model compatibility, access and actual quality are account-dependent and unverified without authorized live calls.

## Setup and activation boundary

Follow [connected AI setup](connected-jobs-ai.md) for existing auth, server-only keys, `AI_WORKER_SECRET` hash installation and processing policy. Migration `20261028030000_p4_cv_import_enrichment.sql` follows the connected migration and photo-reserved `20261028020000` slot. When later applied to Supabase, it prepares a private `cv-imports` bucket capped at 10,000,000 bytes and owned INSERT/read/cleanup policies, including restrictive guards against unrelated permissive policies. No UPDATE/overwrite is permitted. A conflicting public/unbounded bucket fails closed. This migration has only been applied to a disposable local PostgreSQL test cluster, never remotely.

Keep `AI_PAID_INFERENCE=off`. Future authorized activation must deliberately configure server-only stage model names `OPENROUTER_CV_ADMISSION_MODEL`, `OPENROUTER_CV_EXTRACTION_MODEL`, `OPENAI_CV_ADMISSION_MODEL`, `OPENAI_CV_EXTRACTION_MODEL`; career operations reuse `OPENROUTER_MODEL`, `OPENAI_MODEL`, and the existing pinned `OPENROUTER_ENDPOINT`. No model defaults or new credential paths are provided. Provider keys and `AI_WORKER_SECRET` stay Worker-only. OFF rejects mutations before private upload/provider dispatch; owned list/status/cancel remain accessible.

Routes are `/v1/intelligence/imports` (POST bytes, GET list), `/v1/intelligence/imports/:operationId` (GET), `.../:operationId/cancel` (POST), `/v1/intelligence/questions` and `/v1/intelligence/rewrite` (POST). Snapshot ownership/revision is verified before career reservation. Reusing an operation ID returns stored status or an explicit replay result without redispatch. Reload can recover recent owned imports. Interrupted processing becomes unknown after the bounded window; the user can inspect/cancel, not silently regenerate.

Cancellation persists a database fence before object deletion; a late provider completion cannot publish an extraction afterward. Per-account list activity retries bounded cleanup of expired/cancelled sources and acknowledges deletion only after success. **No continuous scheduler is activated**: accounts that never return do not have a guaranteed physical-deletion deadline. A separately authorized periodic cleanup integration, hosted Storage/Auth permission check, parser resource evaluation and real-provider synthetic quality/cost evaluation are required before real-data activation. Source `retain_until` metadata alone is not a deletion guarantee. No compliance, residency or provider retention guarantee is implied.
