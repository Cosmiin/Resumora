# Independent job editor documents (I2)

This bounded editor adapter saves durable, accepted job-specific revisions without advancing the Base editing head. It reuses `resumora-editor-draft/1`, the current editor/preview shapes, owned `target_job_contexts`, and the existing verified-session/Origin/CSRF boundary. It does not publish a canonical CV, create career claims, implement automated matching/tailoring/translation, call a provider or consume tailoring credit. Canonical publication and its confirmations/FKs remain unchanged.

The existing application now opens a job CV from **Jobs → saved vacancy → Open CV for this job**. The same editor, preview and History surfaces load/create, save/reopen, inspect and restore independent accepted job versions. The context banner names the job and returns to Base after pending/uncertain saves and conflicts are resolved. Switching requires a settled saved document, preserving the existing controller's request IDs, retry/recovery and revision checks. On a job save conflict, choose **Reopen saved version** and confirm replacement of the local draft; reopening refreshes the document head and current vacancy pin before further saves. Account changes remount the document coordinator. History inspection remains above the version list.

Job mode exposes manual professional summary, professional/technical competence selection/order/additions, evidence-backed role/optional-entry wording, section/field visibility, template and photo controls. Source facts, dates, employers, original Q&A and import metadata remain pinned; edit those in Base. CV language is fixed to the pinned source in this slice. Unsupported fact edits are rejected rather than discarded or sent to Base. Empty role wording must be replaced with valid wording or hidden using visibility; pending AI proposals are never accepted automatically. The supported edits do not complete AI tailoring, matching, translation, scoring or the five-minute journey.

The job editor extensions in the [ordered migration inventory](../database/traceability.md#migration-order-and-table-coverage) are local implementation only. Hosted application, migration and deployment remain separately gated.

## Stored contract

`resumora-job-editor/1` has explicit document `acceptance: accepted`; each wording change independently requires `acceptance: accepted` and an origin. Pending proposals cannot enter this saved-version API. Sending a proposal does not overwrite an accepted version. A reviewed replacement requires an explicit save and the current document revision.

Each immutable document revision pins one owned immutable Base snapshot UUID/revision. Its facts, original sources, exact career answers and import/review metadata remain in that snapshot. No blanket dual-write, source migration, or duplicate career profile is introduced. Every saved revision pins the owned job ID, nullable reviewed job version and server-computed fingerprint of the job intake/requirements/version. Later Base saves do not change an existing job document. An explicit new accepted save on the same document can select another owned Base snapshot without deleting the document or its history. The caller must submit the complete new source pin, selected references and accepted patches with the current expectedRevision and job pin; all are validated against that exact snapshot. There is no automatic reference remapping or carrying forward of stale proposals. Earlier revisions retain their original source pins, answers and wording. The source columns on the stable document row record creation provenance only; version rows are authoritative for each revision.

`selectedFacts` records exact entity/field/value/source handles from the source snapshot, and `selectedAnswerIds` references confirmed answers. These select evidence eligible for job wording; presentation controls visibility. Editor handles never substitute for canonical UUIDs. Selected facts must satisfy the shared [editor acceptance rule](cv-import-enrichment.md#customer-journey-and-saved-truth), and referenced sources must exist in the pinned snapshot. Wording targets are the current editor's roles and non-language optional entries. Evidence must be that target's context/details/bullets or confirmed target answers with a source handle. Answer provenance uses the shared `answerEvidenceText` contract, including selected option labels and exact free text; the original questions, options and selected IDs remain unchanged in the source snapshot. Job wording authored in the editor uses optional `scope: experience` to replace the description and achievement bullets together; the preview suppresses inherited bullets while that wording is current. Omitting scope preserves historical paragraph-only overlays. Scoped projection carries the accepted wording's origin so manual job text renders without a synthetic Base AI review record; inherited Base AI rewrites keep their existing review-context checks. Only visible context/details, bullets and confirmed answers are attached as evidence. Scope, origin and evidence survive save, reopen, history and restore. Wording cannot replace titles, employers, dates, sources, statuses or answers. Accepting wording is approval of presentation, never factual confirmation. Semantic entailment/quality belongs to the later tailoring proposal workflow; these deterministic persistence checks enforce scope and provenance rather than claiming semantic verification.

`presentation` accepts order, hidden sections/fields, template version and photo overrides. The forward presentation extension also accepts `summaryText` (manual job-local wording, including an empty summary) and ordered `professionalSkillIds`/`technicalSkillIds`. Each competence handle must identify the same pinned source group or an explicit job-local addition of that kind; omitted selections inherit the pinned group. Projection changes only this job document, retaining the immutable source facts. Manual additions remain user-authored wording, not independently verified career evidence. Omitted properties inherit from the pinned snapshot, never from latest Base or global preferences. A null photo explicitly removes it. Well-formed unknown template references survive. Existing Base presentation and accepted wording remain available in the source; job changes overlay only their explicit targets. The [photo lifecycle contract](../frontend/profile-photo.md#authenticated-api-and-private-storage) owns asset validation, history retention and deletion; its unavailable-photo restore fence also applies here.

`localAdditions` supports manual bullets and skills with `scope: job-only`, `origin: user_authored` and namespaced handles. Their projection uses a separate job-local manual source. They do not become career answers or Base facts and cannot be used as independent source evidence by this adapter. Whole-target editing includes visible local bullets in its initial display text without citing them. Toggling a local bullet's visibility clears that target's whole-experience wording so it cannot keep displaying the hidden text; this applies to roles and non-language optional entries and preserves earlier saved revisions. See the [focused regressions](../../apps/web/src/base/job-adapter.test.tsx). Promotion into career knowledge is deferred to a separate explicit operation. General factual replacement, additional wording targets and changes of source are not silently inferred from editor payloads.

The render projection is assembled by `projectJobEditor` using the strict existing decoder and a clone of the pinned source. Generated text goes into the existing `presentation.approvedWording` overlay; original fact values remain intact. API responses return this `draft`, its exact decoded `sourceDraft`, version metadata and the persisted adapter `payload`. Context returns the decoded original pinned source draft for creating a new job document. Every source read uses the existing owned snapshot gateway; the job adapter never reads latest Base or posts a projected draft to Base. The source envelope itself remains obtainable through the existing owned snapshot API. Never send a projected job draft to the Base save endpoint as an automatic side effect.

## Worker endpoints

All routes are under `/v1/jobs/:jobId/cv` and require the existing authenticated session. Writes also require the existing Origin/CSRF headers and JSON media type. The request body is bounded by the existing 1 MiB reader; stored adapter payloads are bounded to 512 KiB. The source snapshot retains its existing independent 1 MiB limit.

| Method/path suffix | Behavior |
|---|---|
| GET `/context` | Server job pin/fingerprint, decoded source draft and the job's original source snapshot/revision; a caller can explicitly select another owned Base snapshot at creation or in a new accepted revision. |
| GET (no suffix) | Active document head or null. With both `documentId` and `versionId` query parameters, load that historical version scoped to the same job/document. |
| GET `/history?documentId=...&beforeRevision=...` | Up to 20 versions newest first; optional exclusive positive revision cursor. |
| POST `/save` | `{requestId, documentId: null or UUID, expectedRevision, payload}`. Null creates a document with expected revision zero; subsequent saves require the exact active document UUID/head. |
| POST `/restore` | `{requestId, documentId, expectedRevision, versionId}`. Append a new immutable revision copying the selected accepted version, preserving earlier versions, `restoredFrom`, and the chosen historical source pin. This is explicitly accepted historical content, not a pending proposal or a claim of current matching validity. The current job fingerprint must still match. |
| POST `/delete` | `{requestId, documentId, expectedRevision}`. Soft-delete only that job document; future reads/restores/saves of it fail. Base, original answers, sources and other job documents remain independent. A later explicit create gets a new document ID. |

Save/restore/delete use the existing transactional idempotency ledger. Identical retries return the same durable revision; changed bodies under the same command/request ID fail. Only the new revision ID is stored in the request result ledger; no payload is put in the provider usage ledger. Deleted documents and inactive accounts fence content replay. Expired request keys retain the existing recovery error rather than silently generating another revision. There is no provider operation or async cancellation workflow in these synchronous persistence commands; callers retain request IDs after uncertain transport outcomes.

The owned job row/context serialize concurrent document writes. CAS prevents concurrent saves/restores from replacing later accepted revisions. A changed job fingerprint/version fences stale save or restore; reading historical versions still returns their historical pin. Tenant/membership and photo row locks order writes against deletion/revocation. New tables are RPC-only with RLS enabled and no direct authenticated/anonymous access; existing exposed table policies are unchanged. Version rows are immutable and document/parent/restore/source/job/photo references carry tenant-scoped FKs.

## Current language versions and export (October 30 correction)

The earlier history/restore description above documents the foundation. The current job contract supersedes it: one current accepted CV per job and language; no old job content/history/restore. CAS IDs/revisions/fingerprints are synchronization metadata. Source-current pins validate the exact owned current source before and during accepted writes. Current job content is self-contained; Base removal preserves current job documents without retaining Base archives. The Job Workflow integration owns the complete current route contract.

Document language is independent of interface language and source language. `documentLocale`/`sourceLocale` use canonical BCP47 identifiers with an application-enabled registry (initially `ro-RO`, `en-GB`). Existing editor `language` remains the rendering compatibility field. Selectors open an accepted language without inference; only **Translate CV** starts P09. The selected accepted authoritative source is pinned by kind/job/document/current ID/revision/full payload fingerprint. Translated sources are not silently chained.

P09 uses the existing structured `cv_rewrite` runner/reservation/replay/cancellation boundary with prompt version `P09.cv-translation.v1`. Its context contains only visible professional components, stable field/fact/evidence references and approved glossary entries. Contacts, name/photo bytes, raw documents, evidence quotations and saved career Q&A are excluded. Component fingerprints also account for associated source dates/employer context. Model output is a proposal, with strict bijection, associations, numbers and protected-term checks; warnings and suggested terminology are metadata, not candidate facts. No prompt/output bodies are logged. Offline injected providers establish deterministic behavior, not real translation quality.

`/v1/document-languages` reads owned source/available versions; `/proposals` starts explicit requests. Proposal advance processes bounded batches through unique existing child operations. Processing/unknown/cancelled results are not automatically reissued. Section review supports manual edits, existing wording, scoped regeneration and section confirmation followed by a full shared-renderer preview. A source or accepted target change fences acceptance and preserves displayed user edits. Atomic acceptance materializes independent current text and small accepted lineage metadata; private proposed output/review are cleared. Refresh touches only selected affected components and retains untouched accepted manual target wording.

Base copies use optional `variant_id` on existing snapshots and the existing editor/history path; default Base remains the sole factual career-context source. Job variants use the existing current job writer with source+target CAS. `document_language_proposals` is private RPC-only pending state, not an accepted content archive. Remove Base must delete every owned Base snapshot variant/history and Base-kind pending proposal/result, while preserving independent current job/language text. The source snapshot deletion trigger also purges matching pending Base proposal records. Existing AI reservation accounting references must be handled by the owning deletion transaction.

Appearance/export shares the accepted structured content, five templates, photo lifecycle and renderer; see [template authoring](../frontend/TEMPLATE_AUTHORING.md#current-document-and-export-boundary). Translation inference remains default-off through existing AI configuration. Production PDF requires separately approved Browser Run capacity, `PDF_BROWSER` binding and `PDF_EXPORT_ENABLED=on`; no resource, paid inference or activation is authorized by these local implementations. Extra locales/RTL, DOCX and real-model quality evaluation remain later work.
