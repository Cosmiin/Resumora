# Optional CV photo

The authenticated editor supports an optional photo in a 200px crop frame. Users can drop/select a file, drag the image, zoom by focused wheel or two-finger pinch, or use small minus/plus and reset-framing controls. Arrow keys move the image, plus/minus zoom, Home resets framing, and a screen-reader output reports the current position. A saved frame is clickable to reopen adjustment. There are no horizontal, vertical or zoom sliders. Circle/square and document visibility remain available. Photo selection and valid crop/shape/visibility changes save automatically after 650ms of inactivity through the existing commit/CAS coordinator. Held pointer gestures, including a pinch with one finger still held, do not write; opening an unchanged saved frame does not save. Close adjustments discards only changes whose debounce has not yet saved. Upload/save failures retain the prior saved photo and local adjustments, with an explicit retry and no automatic retry loop; a successful upload is reused after uncertain CV persistence. Saving/saved/error status distinguishes upload validation/service failures from CV-save conflicts. Photos never invoke AI or enter career facts, Q&A, wording prompts or scoring. An absent/hidden photo leaves no reserved header space.

Each Base CV revision pins its saved photo settings. Restore preserves historical settings when the asset remains available.

## Data and image boundary

`presentation.photo` is optional/null or `{assetId, crop: {version:1, centerX, centerY, zoom}, shape, visible}`. `assetId` is the manifest's UUID, without the canonical graph's `id_` prefix. The strict editor /1 reader accepts older drafts with these fields absent and preserves independent `contributionHtml` and `approvedWording`. A photo commit merges against the latest presentation/text. Historical JSON remains immutable; no migration rewrites drafts. Older clients reject new fields, so deploy compatible readers before enabling uploads and retire stale tabs. Canonical CV 1.0.0 gains backward-compatible optional `document.photo` and `document.photoMode` fields; old snapshots remain valid. Base/profile publication and restore pin settings and same-tenant ready-asset references transactionally at the shared canonical-version insertion boundary.

The browser accepts static JPEG/PNG/WebP up to 10MiB, 24MP and 8192px per side, with a 256px minimum. Headers and animation are checked before native decode. HEIC/SVG/GIF/animated images are rejected with guidance. Browser decode applies EXIF orientation once; a full-frame, white-background sRGB canvas produces a metadata-free JPEG reduced to at most 1600px on its longest side. Extremely narrow sources whose reduced short side is below 256px are rejected. No raw file/name/EXIF is saved. The product explains the resolution reduction before saving. This is non-destructive cropping of the normalized full-frame source, not lossless raw-camera archival.

The Worker independently bounds bytes/dimensions before decoding with pinned free jSquash WASM codecs, decodes/re-encodes to RGB JPEG with a white background, and checks actual dimensions. Direct requests with EXIF/ICC require local normalization rather than guessing orientation or silently misinterpreting profiles. The 1600px server bound keeps native allocations bounded; the original planning document's 24MP limit applies to browser input, not server decode. Native workerd synthetic JPEG/PNG/WebP and 1600px execution were checked without external egress. This establishes runtime functionality, not hosted CPU quota, worst-case latency, device layout or production capacity. Codecs run sequentially per isolate with at most two queued/in-flight normalization requests; overload returns a retryable 429 rather than an unbounded image queue. No remote image service, model or paid image enhancement is configured.

## Authenticated API and private storage

- `POST /v1/photos`: binary bounded JPEG/PNG/WebP with `X-Request-Id` UUID and usual cookie/Origin/CSRF. The same upload ID/body is replayed after uncertain outcomes. Server normalizes before reserving an owned manifest, writes immutable private bytes, reads/checks their SHA-256, then marks ready. Only ready assets can attach to Base editor or canonical CV revisions. No base64 image enters the 1MiB CV JSON route.
- `GET /v1/photos/:id`: owner authorization, checksum verification and a second manifest check fence deletion. Private/no-store bytes, no signed/public URLs, no redirects. Account-scoped component object URLs are revoked on unmount/deletion; a late read cannot restore an invalidated image.
- `DELETE /v1/photos/:id`: logical revocation first, Storage API byte purge second, durable tombstone last. Retry resumes the same deletion. Every existing CV/history reference then becomes unavailable; no old snapshot is mutated or silently resurrected. “Remove from this CV” is a separate versioned null reference and retains other versions' source.
- `POST /v1/photos/cleanup`: authenticated bounded cleanup, at most ten expired unreferenced uploads or pending purges per call. Invoked before a new upload. Sources referenced by retained Base editor or canonical CV history stay retained until explicit deletion/account lifecycle cleanup. The 24h period is an eligibility threshold; no unattended 24h wall-clock purge SLA or remote scheduler is installed. Operations must monitor pending purges and arrange an authorized maintenance/account-deletion integration before production retention promises.

The prepared additive migration is `20261028020000_p3_cv_photos.sql`: manifests, editor and canonical CV reference bookkeeping, trusted Worker validation gate and private bucket policies. SQL locks protect attach/restore against concurrent deletion; source checksum/body mismatches conflict. Storage keys are opaque tenant UUID/asset UUID paths. Authenticated Storage writes are only allowed for an existing reserved owned manifest; clients cannot create/finalize it without the Worker-only secret. Bytes cannot be updated/upserted after verification. Owner-controlled races can only leave a non-ready failed upload; they cannot attach unverified bytes. Broad pre-existing Storage policies are constrained for this bucket by restrictive guards.

Storage policies use operation-aware helpers to permit authenticated content reads and deletion's metadata selection separately. Signing URLs, listing, overwriting and reading purge-pending bytes are denied. Migration fails for review if an existing bucket conflicts or the target lacks `storage.allow_only_operation(text)`; no broad-policy fallback. The isolated PostgreSQL Storage schema/operation helper is a **test double for RLS semantics**, not a real Storage service.

## Setup and remaining acceptance

No hosted migration, bucket creation, secret installation, deployment, real-account/image access or paid call was performed. The default absent `PHOTO_WORKER_SECRET` fails closed with `photoUnavailable`; preserving text editing does not depend on configuring photos. After separate target approval, provision a high-entropy server-only 32–128 character `[A-Za-z0-9_-]` secret in Worker binding `PHOTO_WORKER_SECRET` and its SHA-256 (UTF-8) in restricted `app.photo_worker_config`. No raw secret/default value belongs in Git, browser/Vite settings, logs or general database gateways. This is a trusted normalizer attestation in addition to existing user auth/RLS, not a replacement identity or service-role credential. Never use a privileged database/storage key as a browser token. Runtime secret validity and Storage operation names require target preflight; follow the existing database runbook without applying it from this task.

Deletion confirmation explicitly warns: **“It will also be removed from your CVs and will no longer be available in historical versions. Downloaded copies cannot be recalled.”** Physical erasure from backups follows the independently verified deployment policy; already displayed/downloaded bytes cannot be recalled. Actual PDF/export byte invalidation and account-deletion integration remain future module acceptance; do not advertise those absent integrations as complete. Restoring an unavailable-photo snapshot fails safely; removing/replacing the photo on the retained current draft remains possible.

Focused verification uses `apps/api/tests/photos.test.mjs`, `photo-runtime.test.mjs`, the composed binary-CSRF coverage in `auth-runtime.test.mjs`, `apps/web/src/photo/photo.test.tsx`, and `python3 scripts/db/test.py --suite photos` with native local PostgreSQL. ### Bounded failure diagnostics

Photo failures retain their existing HTTP status/code and include an allowlisted operational `phase`: configuration, input, normalize, reserve, storage_write, storage_verify, finalize, cleanup, read or delete. The typed client accepts only these phases. User copy distinguishes account reservation, private file save/verification and final confirmation, while preserving the previous persisted photo and existing explicit retry/CAS behavior.

Worker diagnostics are limited to `photo-failure {phase,httpStatus,code}`, `photo-database {operation,httpStatus,code,reason}` and `photo-storage-response {operation,httpStatus,code}`. Codes/reasons are allowlisted; unknown values become `UNCLASSIFIED` or the existing safe fallback. No raw exception, request/body, filename, image bytes, object path, user/asset identifier, credential or hash is logged. No diagnostic ledger or new database write is introduced.

A reserved asset alone is not proof of a Storage write/finalize cause. A successful synthetic Worker normalizer→authenticated gateway→reserve/write/verify/finalize test establishes parameter/runtime compatibility only. Diagnose a live failure from the actual safe phase/status/code receipt before changing configuration, policy, bucket permissions or stored data. An owner retry must be coordinated separately; agents must not replay owner images to collect diagnostics.
