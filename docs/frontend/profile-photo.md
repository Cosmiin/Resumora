# Optional CV photo

The authenticated Base editor supports choosing one optional image, dragging or moving its frame with horizontal/vertical/zoom sliders and buttons, selecting circle/square, previewing, then explicitly saving the photo. Selecting or moving never uploads bytes or changes the saved draft. Save validates private bytes and saves one revision through the existing editor coordinator. Photos never invoke AI and never enter career facts, Q&A, wording prompts or scoring. An absent/hidden photo leaves no reserved header space.

The owner approved **use the new Base photo in the next tailored draft revision**, with explicit job-only overrides (including no photo) retained until “Use Base.” For jobs following Base, `save_job_cv_checkpoint` pins the latest saved Base editor photo, crop, circle/square choice and visibility in each new canonical document revision. `document.photoMode` is `base` or `override`; an omitted mode preserves the previous job mode, defaulting to `base` for new documents. Set `photoMode: "override"` and `photo` to customize a job; set `photoMode: "base"` to resume inheritance. Later Base changes never rewrite existing versions. Job-only changes never modify Base. Restore creates a new version with the historical photo settings and mode; deleted assets cannot be restored. These backend commands do not add a tailoring UI or PDF export. Actual exporter integration remains outstanding.

## Data and image boundary

`presentation.photo` is optional/null or `{assetId, crop: {version:1, centerX, centerY, zoom}, shape, visible}`. `assetId` is the manifest's UUID, without the canonical graph's `id_` prefix. The strict editor /1 reader accepts older drafts with these fields absent and preserves independent `contributionHtml` and `approvedWording`. A photo commit merges against the latest presentation/text. Historical JSON remains immutable; no migration rewrites drafts. Older clients reject new fields, so deploy compatible readers before enabling uploads and retire stale tabs. Canonical CV 1.0.0 gains backward-compatible optional `document.photo` and `document.photoMode` fields; old snapshots remain valid. Base/profile publication, job checkpoints and restore pin settings and same-tenant ready-asset references transactionally at the shared canonical-version insertion boundary.

The browser accepts static JPEG/PNG/WebP up to 10MiB, 24MP and 8192px per side, with a 256px minimum. Headers and animation are checked before native decode. HEIC/SVG/GIF/animated images are rejected with guidance. Browser decode applies EXIF orientation once; a full-frame, white-background sRGB canvas produces a metadata-free JPEG reduced to at most 1600px on its longest side. Extremely narrow sources whose reduced short side is below 256px are rejected. No raw file/name/EXIF is saved. The product explains the resolution reduction before saving. This is non-destructive cropping of the normalized full-frame source, not lossless raw-camera archival.

The Worker independently bounds bytes/dimensions before decoding with pinned free jSquash WASM codecs, decodes/re-encodes to RGB JPEG with a white background, and checks actual dimensions. Direct requests with EXIF/ICC require local normalization rather than guessing orientation or silently misinterpreting profiles. The 1600px server bound keeps native allocations bounded; the original planning document's 24MP limit applies to browser input, not server decode. Native workerd synthetic JPEG/PNG/WebP and 1600px execution were checked without external egress. This establishes runtime functionality, not hosted CPU quota, worst-case latency, device layout or production capacity. Codecs run sequentially per isolate with at most two queued/in-flight normalization requests; overload returns a retryable 429 rather than an unbounded image queue. No remote image service, model or paid image enhancement is configured.

## Authenticated API and private storage

- `POST /v1/photos`: binary bounded JPEG/PNG/WebP with `X-Request-Id` UUID and usual cookie/Origin/CSRF. The same upload ID/body is replayed after uncertain outcomes. Server normalizes before reserving an owned manifest, writes immutable private bytes, reads/checks their SHA-256, then marks ready. Only ready assets can attach to editor or canonical CV revisions. No base64 image enters the 1MiB CV JSON route.
- `GET /v1/photos/:id`: owner authorization, checksum verification and a second manifest check fence deletion. Private/no-store bytes, no signed/public URLs, no redirects. Account-scoped component object URLs are revoked on unmount/deletion; a late read cannot restore an invalidated image.
- `DELETE /v1/photos/:id`: logical revocation first, Storage API byte purge second, durable tombstone last. Retry resumes the same deletion. Every existing CV/history reference then becomes unavailable; no old snapshot is mutated or silently resurrected. “Remove from this CV” is a separate versioned null reference and retains other versions' source.
- `POST /v1/photos/cleanup`: authenticated bounded cleanup, at most ten expired unreferenced uploads or pending purges per call. Invoked before a new upload. Sources referenced by retained editor or canonical CV history stay retained until explicit deletion/account lifecycle cleanup. The 24h period is an eligibility threshold; no unattended 24h wall-clock purge SLA or remote scheduler is installed. Operations must monitor pending purges and arrange an authorized maintenance/account-deletion integration before production retention promises.

The prepared additive migration is `20261028020000_p3_cv_photos.sql`: manifests, editor and canonical CV reference bookkeeping, trusted Worker validation gate and private bucket policies. SQL locks protect attach/restore against concurrent deletion; source checksum/body mismatches conflict. Storage keys are opaque tenant UUID/asset UUID paths. Authenticated Storage writes are only allowed for an existing reserved owned manifest; clients cannot create/finalize it without the Worker-only secret. Bytes cannot be updated/upserted after verification. Owner-controlled races can only leave a non-ready failed upload; they cannot attach unverified bytes. Broad pre-existing Storage policies are constrained for this bucket by restrictive guards.

Storage policies use operation-aware helpers to permit authenticated content reads and deletion's metadata selection separately. Signing URLs, listing, overwriting and reading purge-pending bytes are denied. Migration fails for review if an existing bucket conflicts or the target lacks `storage.allow_only_operation(text)`; no broad-policy fallback. The isolated PostgreSQL Storage schema/operation helper is a **test double for RLS semantics**, not a real Storage service.

## Setup and remaining acceptance

No hosted migration, bucket creation, secret installation, deployment, real-account/image access or paid call was performed. The default absent `PHOTO_WORKER_SECRET` fails closed with `photoUnavailable`; preserving text editing does not depend on configuring photos. After separate target approval, provision a high-entropy server-only 32–128 character `[A-Za-z0-9_-]` secret in Worker binding `PHOTO_WORKER_SECRET` and its SHA-256 (UTF-8) in restricted `app.photo_worker_config`. No raw secret/default value belongs in Git, browser/Vite settings, logs or general database gateways. This is a trusted normalizer attestation in addition to existing user auth/RLS, not a replacement identity or service-role credential. Never use a privileged database/storage key as a browser token. Runtime secret validity and Storage operation names require target preflight; follow the existing database runbook without applying it from this task.

Deletion confirmation explicitly warns: **“It will also be removed from your existing tailored CVs and will no longer be available in historical versions. Downloaded copies cannot be recalled.”** Physical erasure from backups follows the independently verified deployment policy; already displayed/downloaded bytes cannot be recalled. Actual PDF/export byte invalidation and account-deletion integration remain future module acceptance; do not advertise those absent integrations as complete. Restoring an unavailable-photo snapshot fails safely; removing/replacing the photo on the retained current draft remains possible.

Focused verification uses `apps/api/tests/photos.test.mjs`, `photo-runtime.test.mjs`, the composed binary-CSRF coverage in `auth-runtime.test.mjs`, `apps/web/src/photo/photo.test.tsx`, and `python3 scripts/db/test.py --suite photos` with native local PostgreSQL. The photo suite necessarily includes unchanged editor draft cases and infrastructure checks. Browser/native pointer, touch, screen-reader, 390×844/1366×768/200% zoom, real Auth/Storage bucket operations and actual PDF checks remain unverified. The owner subsequently permitted isolated synthetic-local checks with disposable data and external networking denied. One named Chrome bridge start returned BRIDGE_NOT_READY before any page visit; it was stopped, with no fallback/retry or real-profile/account claim. Hosted setup remains separately authorized.
