# Remove the Job Product Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove every active job-related feature and all attributable data across the existing hosted Resumora project, retaining authentication and the complete Base CV product.

**Architecture:** Preserve the current working implementation, extract shared primitives, reduce application contracts and endpoints to Base CV, and apply a forward removal migration. Test in isolation, then perform one maintenance cutover with an exact storage-deletion manifest and preservation checks. Historical migrations and Git history remain; no compatibility service or job-data archive remains active.

**Tech Stack:** Existing npm workspaces; Node 22.23.4 (`.nvmrc`), TypeScript, React/Vite, local Wrangler API, native PostgreSQL tests, hosted Supabase `aquvhqbkvrtzhbmezkci`, existing OpenRouter/OpenAI integrations.

**Spec:** `docs/superpowers/specs/2026-11-04-remove-job-product-design.md` (user approved 4 November 2026).

**Status:** Planning complete; implementation, test execution and hosted mutation have not started. All paths below are repository-relative unless explicitly stated otherwise.

## Global Constraints

- “Use a new removal migration. Keep applied historical migrations and Git history. Clean current documentation, tests, fixtures and scripts.”
- “Keep unfinished CV, enrichment and language work. Audit that work separately after this removal project; do not use removal as a pretext for unrelated fixes or redesign.”

- Operate the existing managed service with `dev:start`, `dev:status`, `dev:stop` and `dev:doctor`. No second unmanaged API/frontend/import processor alongside it. Do not deploy a new cloud copy of the app.
- Do not delete other worktrees, reset user data, rewrite Git history, change models/providers, or perform the deferred CV audit.
- Full deletion means mutable application stores under our control; historical migrations/Git and inaccessible copies have the explicit limits recorded in the spec.

## Review Focus

1. **Late writers:** stale tabs, extension credentials, background callbacks or old request receipts must not recreate removed resources (Tasks 3, 5, 7, 8).
2. **Shared ownership:** an asset, routine or ledger used by both products must preserve its Base use while losing its job records/branches (Tasks 2, 3, 5, 6).
3. **Hidden historical content:** restore, translation, draft recovery or cached AI output must not bring back attributed job-derived Base content (Tasks 4, 5).
4. **Partial destructive cleanup:** a failed storage deletion after SQL commit must be retryable without a data archive or lost deletion manifest (Tasks 6, 8).
5. **Existing unfinished work:** isolation and integration must carry the complete current Base implementation, not just committed HEAD, and must preserve concurrent owner changes (Tasks 1, 7, 8).

## Failure and recovery boundaries

- Before SQL commit: refuse unsafe classification; a failed transaction must leave data unchanged. An aborted rollout may reopen the old application only if no destructive step committed and the user is told removal did not occur.
- After SQL commit: retain maintenance and repair forward. Do not run an older app against the reduced schema or restore a backup that resurrects job data.
- After partial storage deletion: retry from the owner-only manifest, treating verified absence as success. Do not remove that manifest until every required deletion is confirmed.
- Before source integration: if the live tree diverged, reconcile and test the delta. Never overwrite newer retained work to meet a maintenance schedule.
